# Phase 2: The Infrastructure Masterclass (Ultra-Detailed)

This document is the "Black Belt" guide to deploying the Crawler's data backbone. We are building a system that can handle millions of URLs, maintain transactional integrity, and provide a real-time event stream.

---

## 🏗️ 1. The Global Architecture: The "Event Mesh"

Before we look at code, you must understand the **flow of data**. In a professional crawler:
1.  **Storage:** Postgres saves the "Source of Truth" (URLs, Status, Results).
2.  **Detection:** Debezium (running in Kafka Connect) watches Postgres.
3.  **Transport:** Kafka moves the message from the "Database Layer" to the "Processor Layer".
4.  **Visibility:** Kafdrop/AKHQ lets us "see" the messages in the pipes.

### 💡 Why this is better than a direct database connection?
If the `Processor` is overwhelmed, Kafka acts as a **Buffer**. It stores the crawl results safely. The Processor can consume them at its own pace. If we used only a database, the DB connections would exhaust, and the system would crash.

## 📁 2. The Umbrella Chart: Mastery of Structure

We use an **Umbrella Chart**. This is a Helm chart that has no logic of its own but acts as a "Box" for other charts.

**Directory Structure:**
```text
k8s/helm/infra/
├── Chart.yaml             # The "Manifest" of our dependencies
├── values.yaml            # The "Grand Config" (Settings for all tools)
├── .helmignore            # Keeps our package clean
├── charts/                # [AUTOGENERATED] Managed by "helm dep update"
└── templates/             # Custom "Mismatched" logic
    ├── custom-pvc.yaml    # For special storage needs
    ├── configmap-init.yaml# SQL scripts to run on DB startup
    └── network-policy.yaml# Firewall rules inside K8s
```

## 📥 3. The Dependency Manifest (`Chart.yaml`)

This file tells Helm exactly which versions of professional software to download.

```yaml
apiVersion: v2
name: crawler-infra
description: A high-performance data backbone for the web crawler.
type: application
version: 1.0.0
appVersion: "1.0.0"

dependencies:
  # --- RELATIONAL STORAGE ---
  - name: postgresql
    version: 15.5.24  # Stick to a specific version for stability
    repository: https://charts.bitnami.com/bitnami
    condition: postgresql.enabled # Toggle via values.yaml

  # --- MESSAGE BUS (THE BRAIN) ---
  - name: kafka
    version: 26.11.2
    repository: https://charts.bitnami.com/bitnami
    condition: kafka.enabled

  # --- COORDINATION ---
  - name: zookeeper
    version: 12.x.x
    repository: https://charts.bitnami.com/bitnami
    condition: zookeeper.enabled

  # --- UI & VISIBILITY ---
  - name: akhq
    version: 0.2.x
    repository: https://akhq.io/
    condition: akhq.enabled
```

### 🎓 Senior Note: The `condition` field
Setting `condition: postgresql.enabled` allows you to turn off the database during testing or if you decide to use an external DB (like AWS RDS) without changing the chart structure.

## 🐘 4. PostgreSQL: Deep Dive & Configuration

Postgres in K8s is a "StatefulSet". 

### 💡 The WAL (Write Ahead Log) Config
For **Debezium** to work, Postgres must record every change in a special format. This is called "Logical Decoding".

**In your `values.yaml`:**
```yaml
postgresql:
  enabled: true
  auth:
    database: crawler
    username: crawleradmin
    password: "choose-a-strong-password"
  
  # Persistence logic
  primary:
    persistence:
      enabled: true
      size: 50Gi # Large enough for years of crawl history
      storageClass: "standard" # Use 'longhorn' or 'gp2' in cloud
    
    # ADVANCED: Tuning for Debezium & Performance
    extendedConfiguration: |
      # 1. Debezium Requirements
      wal_level = logical
      max_replication_slots = 10
      max_wal_senders = 10
      
      # 2. Performance Tuning (The "Pro" settings)
      max_connections = 200
      shared_buffers = 256MB
      effective_cache_size = 768MB
      maintenance_work_mem = 64MB
      checkpoint_completion_target = 0.9
      wal_buffers = 7864kB
      default_statistics_target = 100
      random_page_cost = 1.1
      effective_io_concurrency = 200
```

### 💡 Why `wal_level = logical`?
By default, Postgres logs changes in "Physical" format (binary math). Debezium needs "Logical" format (readable row changes). If you forget this, Debezium will connect but see **Zero** data.

## 🎡 5. Kafka: The High-Throughput Engine

Kafka is complex because it's a "Distributed System" inside a "Distributed System" (K8s).

### 💡 Components of Kafka Config
1.  **Bootstrap Servers**: How apps find the entry point.
2.  **Listeners**: How traffic enters the pod.
3.  **Partitions**: How many parallel "threads" a topic has.

**In your `values.yaml`:**
```yaml
kafka:
  enabled: true
  replicaCount: 3 # MUST be 3 for high availability
  
  # Networking logic
  listeners:
    client:
      protocol: PLAINTEXT
      port: 9092
    interbroker:
      protocol: PLAINTEXT
      port: 9093
  
  # Performance: Controlling JVM (Java Virtual Machine) memory
  # Lesson: Java is a memory-hog. If you don't limit it, it crashes the Node.
  heapOpts: "-Xmx1024m -Xms512m"
  
  resources:
    limits:
      memory: 2Gi # Room for the heap + OS cache
      cpu: 1000m
    requests:
      memory: 1Gi
      cpu: 500m

  # Storage logic
  persistence:
    enabled: true
    size: 100Gi # Kafka stores the "history" of the crawl
```

### 💡 Senior Note: Replication Factor
Always set your "Topic Replication Factor" to **3**. This means if one server catches fire, your crawl data exists on two other servers. K8s will automatically promote one of the survivors to "Leader".

## 🐒 6. Zookeeper: The Librarian

Zookeeper keeps track of which Kafka server owns which data. 

### Does it need 3 nodes?
**YES.** Zookeeper uses Quorum logic. 
*   If you have 1 node, it's a single point of failure.
*   If you have 2 nodes, and they disagree, they both stop (Split Brain).
*   If you have 3 nodes, they can "Vote". 2 can outvote 1. This is the minimum for stability.

**In your `values.yaml`:**
```yaml
zookeeper:
  enabled: true
  replicaCount: 3
  persistence:
    enabled: true
    size: 5Gi
```

## 🌉 7. Debezium & Kafka Connect: The Integration Layer

This is the most "custom" part of the infra. You are essentially deploying a "Cluster of Workers".

### 💡 How to deploy Debezium via Helm?
We use the Kafka Connect chart but point it to the Debezium Docker Image.

**In your `values.yaml`:**
```yaml
# Add this as a custom value or separate deployment
debezium:
  image:
    repository: debezium/connect
    tag: "2.5.0.Final"
  config:
    bootstrapServers: "infra-kafka:9092"
    groupId: "crawler-cdc-group"
    # Where to store internal offsets (Don't lose track of where we are in Postgres)
    offsetStorageTopic: "debezium_offsets"
    configStorageTopic: "debezium_configs"
    statusStorageTopic: "debezium_status"
```

### 💡 The Secret Command: Creating the Connector
Once the Pod is running, you must send a "Rest API Call" to it to start the engine:
```bash
curl -i -X POST -H "Accept:application/json" -H  "Content-Type:application/json" http://localhost:8083/connectors/ -d '{
  "name": "crawler-connector",
  "config": {
    "connector.class": "io.debezium.connector.postgresql.PostgresConnector",
    "database.hostname": "infra-postgresql",
    "database.port": "5432",
    "database.user": "crawleradmin",
    "database.password": "password",
    "database.dbname" : "crawler",
    "topic.prefix": "crawler_events",
    "plugin.name": "pgoutput"
  }
}'
```

## 🛡️ 8. Security & RBAC (Role Based Access Control)

In a real company, the `Parser` should not be allowed to talk to the `Postgres` database. Only the `Processor` and `Debezium` should.

### 💡 Network Policy (The FireWall)
You can write a file in `templates/network-policy.yaml`:

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: restrict-postgres
spec:
  podSelector:
    matchLabels:
      app.kubernetes.io/name: postgresql
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: processor # Allow processor
        - podSelector:
            matchLabels:
              app: debezium # Allow debezium
```

### 💡 Why this matters?
If a hacker breaks into your `Parser` (which is exposed to the internet), they cannot steal your database data because the K8s Network Policy will block the traffic!

## 📈 9. Monitoring: The "SRE" View

Infrastructure without monitoring is like driving blind.

### 💡 Metrics Exporting
Most Bitnami charts have a `metrics` sidecar. You should enable it:

```yaml
postgresql:
  metrics:
    enabled: true # Spawns a small pod that speaks to Prometheus
kafka:
  metrics:
    kafka-exporter:
      enabled: true
```

### 💡 Key Metrics to Watch:
*   **Kafka Lag**: If this number is growing, it means your `Processor` is too slow, and data is piling up.
*   **Postgres CPU**: If this is high, you need to add "Indexes" to your database.
*   **Disk Pressure**: If Kafka runs out of disk, it **locks itself** and stops accepting data. Always set alerts for 80% disk usage.

## 📦 10. Advanced Helm Techniques

### 💡 1. The `tpl` Function
Sometimes you want your config files to use variables from `values.yaml`. 
Example: A custom script in a ConfigMap.
```yaml
data:
  init.sql: |
    CREATE USER {{ .Values.postgresql.auth.username }};
```
If you use the `tpl` function, Helm will replace the `{{ ... }}` inside the string!

### 💡 2. Global Variables
If you want the same "Registry" URL used for all images, put it in a `global` block:
```yaml
global:
  imageRegistry: "my-private-repo.com"
```
Subcharts automatically read from the `global` block.

1. `helm uninstall crawler-infra -n crawler`

## 🧩 13. Deep Troubleshooting Manual

### 1. The "Waiting for PVC" Trap
If your pod stays in `Pending` forever, run `kubectl describe pod [NAME]`.
*   If it says `persistentvolumeclaim ... not found`, it means your `StorageClass` name is wrong.
*   Check available classes with `kubectl get sc`.

### 2. Kafka "No Leader" Error
This usually means Zookeeper is down. Kafka cannot decide who is in charge without its librarian. Fix Zookeeper first, then restart Kafka.

### 3. Postgres "OOM Killed"
Parsers and Crawlers can generate massive bursts of data. If Postgres isn't given enough RAM for its buffers, it will crash.
*   **Fix:** Increase `resources.limits.memory` in `values.yaml`.
